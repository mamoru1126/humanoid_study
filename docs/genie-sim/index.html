  1. Genie Sim は、NVIDIA Isaac Sim の上に載る「場面づくり、データ収集、評価」の一式である。方策（policy）は中に持たない。WebSocket でつないだ外のサーバに任せる。
  2. いちばんの売りは、シミュレーションでの成績が実機の成績と合うことを数字で示した点にある。論文は、シミュレーションと実機の成功率の決定係数を 0.94、シミュレーションのデータだけで学習した方策の実機での成功率を平均 0.83（実機のデータで学習した場合は 0.75）と報告している[2]。
  3. RTX 3090 は NVIDIA の動作確認の対象に入っていないが、要件（RT コアがあること、VRAM 16 GB 以上）は満たす[3]。Genie Sim のコードが 3090 をはっきり弾くのは、布などを扱うソルバ libuipc だけで、影響するのはアセットの索引にある 150 タスクのうち 3 つである。ただし、この資料の時点で、3090 の実機では確かめていない。
  4. 勉強になるのは、方策とシミュレータの境目である。観測を受け取り、行動のまとまりを返し、それが 30 Hz で実行され、条件で採点される。この一周を、付属の 110 行の「動かない方策」で回すところから始められる。
  5. 最初の目標は 3 段階に分ける。カメラ画像を 1 組保存する。動かない方策で評価を最後まで通し、録画する。2 台目の 3090 に置いた方策サーバをつなぐ。

1Genie Sim とは何か

Genie Sim は、AgiBot（智元機器人）が開発しているロボット学習向けのシミュレーション基盤である。2026 年 1 月の CES で 3.0 が発表され、コード、アセット、データセットが公開された[4]。コードのライセンスは MPL-2.0 である[1]。

物理や描画を自前で持つシミュレータではない。物理と描画は NVIDIA Isaac Sim に任せ、その上で、ロボット学習に要る 4 つの仕事を受け持つ。材料（物体と環境）をそろえる、場面を作る、データを集める、方策を評価する、の 4 つである。学習そのものと、学習した方策を動かすサーバは、外に置く。

1.2　版に注意する

Genie Sim は更新が速い。発表時の 3.0 は Isaac Sim 5.1 を土台にしていたが、この資料で読んだ 2026-11-13 の版（VERSION は 3.6.0）は Isaac Sim 6.2、ROS 2 Jazzy、Python 3.12 が土台で、5.1 以前の構成は終了扱いになっている[1]。Web の記事や動画の手順は古い版のものが多い。手順は本体の README.md と docker/README.md を正とする。このリポジトリのスクリプトは、読んだ版に固定して取得する。

2どういう仕組みで動いているか

2.1　層の重なり

動かすときの構成は、外から順に 4 層になる。PC、コンテナ、Isaac Sim、Genie Sim の評価プログラムである。方策サーバはその外にあり、同じ PC でも別の PC でもよい。

Isaac Sim の中身を、Gazebo を知っている人向けに言い換えるとこうなる。場面は SDF ではなく USD（OpenUSD）で書く。物理は PhysX が既定で、剛体の計算は初期設定では CPU で行う（enable_gpu_dynamics が偽。11 個のタスクは設定で GPU に切り替えている）。描画は RTX のレイトレーシングで、初期設定は RaytracedLighting である。これらを Omniverse Kit というアプリの土台が束ねていて、Python から起動して操れる。Genie Sim の評価プログラムは、まさにそう使っている。

2.2　起動すると何が起きるか

geniesim docker up は、本体の docker/start.sh を呼んでコンテナを起動する。コンテナの中では docker/entrypoint.sh が準備を進める[1]。

  1. コンテナを起動する。GPU をすべて渡し（--gpus all）、ホストのネットワークをそのまま使い（--network=host）、特権つき（--privileged）で動かす。本体のコードを /workspace に、アセットを /geniesim_assets に、キャッシュの置き場をホーム以下につなぐ。
  2. 利用者の番号を合わせる。コンテナの中の利用者 isaac-sim の番号を、PC の利用者の番号に書き換える。コンテナが作ったファイルの持ち主が PC の利用者になり、あとで消せなくなることがない。
  3. 本体を登録する。/workspace の Python パッケージを「編集可能」の形で入れる。PC 側でコードを書き換えると、作り直さずにコンテナの中へ反映される。
  4. libuipc を確かめる。布などの変形する物体を扱うソルバである。RTX 3090 ではここで「使えない」と表示され、そのまま先へ進む（4.2 節）。
  5. 準備の完了を知らせる。ログに GENIESIM_READY と出る。

設計の考え方は、重くて変わらないもの（Isaac Sim、ROS 2、依存パッケージ）をイメージに焼き、軽くてよく変わるもの（本体のコード、アセット、出力）を外からつなぐ、というものである。シェーダのキャッシュは名前つきのボリュームに置かれ、コンテナを消しても残る。

2.3　評価の一周

geniesim benchmark run タスク名 は、コンテナの中で評価プログラム（app/app.py）を起動する。プログラムは Isaac Sim を立ち上げ、場面とロボットを読み込み、方策サーバとやりとりしながらエピソードを進める[1]。

数字は本体のコードによる。物理は 120 Hz、描画は 60 Hz を基準に進む（physics_step、rendering_step）。方策が返す行動は、複数の時刻ぶんをまとめた「チャンク」で、環境は 1 ステップに 1 点ずつ、関節の目標位置として与える。1 ステップは 1/30 秒に当たり、30 ステップごとにタスクの条件を判定する（pi_env.py の _CHUNK_STEPS = 30）。

GPU の負荷を抑える工夫が 1 つ入っている。カメラ画像が要るのは方策に観測を渡すときだけなので、行動を再生している間は描画を要求しない（task_benchmark.py）。

次の推論の前には、腕が目標に収まるのを最大 1 秒待つ（infer_settle_timeout）。方策の応答を待つ間に物体が重力でずれるのを避けたいときは、設定 pause_physics_during_inference を真にすると、待ち時間のあいだ物理を止められる。初期設定は止めない。推論が遅い構成では、この設定で結果が変わりうる。

2.4　方策との約束

評価プログラムと方策サーバは、WebSocket の上で msgpack をやりとりする。形は JSON-RPC に似ていて、要求は {"method": "infer", "params": {...}}、応答は {"result": {...}} である（corobotpolicy.py）[1]。初期設定のつなぎ先は localhost:8999 で、--infer-host=ホスト:ポート で変える。

向き項目中身
要求images頭（head）、左手首（hand_left）、右手首（hand_right）のカメラ画像。JPEG で送る
要求states腕、グリッパ、腰、頭の関節の状態と、手先の位置姿勢（end_pose）。台車のあるロボットでは台車の状態も入る
要求prompt指示文。例は「Right arm picks up red block on the table」
要求robot_type、task_name、episode_idx などロボットの種類、タスクの名前、エピソードの番号と区切り
応答left_arm、right_arm腕の行動のチャンク。種類（kind）は、関節角の絶対値 JOINT_ABS か、手先の位置姿勢の絶対値 EEF_ABS。後者は評価プログラムが逆運動学で関節角に直す
応答left_effector、right_effectorグリッパの行動のチャンク
応答waist、head、wheels腰、頭、台車。使うロボットとタスクのときだけ

この約束さえ守れば、方策の中身は何でもよい。本体に付属の scripts/fake_infer_server.py は、受け取った関節角をそのまま 30 点ぶん返すだけの 110 行のサーバで、ロボットは姿勢を保つ。モデルなしで評価の一周を回すために用意されている。自分の方策サーバを書くときの、いちばん短い手本でもある。

2.5　タスクと採点

タスクは、設定ファイル 1 つ（ロボット_分類_名前.yaml）と、場面の組からなる。場面 1 つは 1 つのディレクトリで、主なファイルは次の 4 つである。g2op_if_pick_block_color（色を指定してブロックを取る）には場面が 20 個あり、どの場面にも指示が 5 つある[1]。評価は、指示 1 つを 1 エピソードとして順に行う。

ファイル中身
scene.usda場面そのもの。机や物体の配置を USD で書いたもの
scene_info.json場面にある物体の説明。色、形、大きさ、材質、位置
instructions.jsonこの場面で出す指示文の一覧と、対象の物体、使う腕
problems.json指示ごとの採点の条件

採点の条件は、小さな部品を組み合わせて書かれている。「右腕で赤いブロックを取る」の条件は、次の 2 段である。

"ActionList": [
  { "ActionSetWaitAny": [
      { "Follow": "赤いブロック|[0.1,0.2,0.1]|right_gripper" },
      { "StepOut": 200 } ] },
  { "ActionSetWaitAny": [
      { "PickUpOnGripper": "赤いブロック|right_gripper" },
      { "StepOut": 200 } ] }
]

物体の名前は、実際には benchmark_building_blocks_378069fe のような識別子である。読みやすさのために置き換えた。

1 段目は「右のグリッパが赤いブロックの近く（指定した範囲）に来る」、2 段目は「赤いブロックが右のグリッパに持ち上げられる」である。各段は、条件が成り立つか、200 ステップが過ぎるかの、早いほうで終わる（ActionSetWaitAny）。方策が何もしなければ、1 段目が時間切れになってエピソードが終わる。結果は evaluate_ret_00.json に書かれる。

指示文と採点の条件は、手で書いたものではない。場面の説明から LLM が指示文を作り、その指示文から LLM が採点の条件を作る、という順で生成されている（evaluator/generators）。条件の語彙（Follow、PickUpOnGripper、Ontop、Inside、Upright など）と、組み合わせ方（どれか 1 つ、全部、順に）を決めておき、組み立てを LLM に任せる作りである。

2.7　アセットの配り方

アセットは、Python のパッケージの形をした 1 つの置き場（geniesim_assets）にまとまっている。全部を落とす必要はない。geniesim assets download は、指定したタスクが実際に参照するファイルだけを取得する。参照の関係は事前に調べて索引に固めてあり、取得したファイルは SHA256 で中身を確かめる。同じ中身のファイルはハードリンクで 1 つにまとめる[1]。

取得の単位タスク数容量
タスク 1 つ15.13 GiB
指示理解（g2op_if）106.42 GiB
操作（manip）107.32 GiB
空間理解（spatial）85.39 GiB
外乱への強さ（robust）506.42 GiB
全身（wbc）88.60 GiB
索引にある全部15017.70 GiB

容量は、重複を除いた値。索引から計算した。「タスク 1 つ」は g2op_if_pick_block_color の値。g2op_if の値は、CLI の geniesim assets plan g2op_if の表示（10 タスク、1,137 ファイル、6.42 GiB）と一致する。

タスク 1 つでも 5 GiB を超えるのは、背景に使う全天の画像（HDR と EXR、合わせて約 5.3 GiB）が、どのタスクにも含まれるからである。評価のたびに背景を取り替えて、見た目の違いへの強さを確かめるために入っている。そのため、タスクを増やしても容量はあまり増えない。

3何がすごいのか

ここに書くことは、論文[2]と本体の説明[1]による。自分で再現して確かめたものではない。

3.1　シミュレーションの成績が、実機の成績と合う

シミュレーションで評価する意味があるかどうかは、そこでの順位が実機でも保たれるかで決まる。論文は、学習の条件が違う 16 通りの方策を、実機とシミュレーションの両方で 50 回ずつ試し、成功率を突き合わせた。決定係数は 0.94、回帰直線の傾きは約 1.025 だった[2]。シミュレーションで良い方策は実機でも良く、成功率の値そのものもほぼ同じ、という結果である。

もう 1 つの結果は、シミュレーションのデータだけで学習した方策を、そのまま実機で動かしたものである。方策は π0.5 を調整したもの、ロボットは AgiBot G1 で、8 つのタスクの平均は 0.83 だった。実機のデータで学習した場合の 0.75 を上回る。

読むときの注意。データの量はそろっていない。論文の注記では、シミュレーションのデータは 1 タスク 500 から 1,500 エピソード、実機のデータは 500 エピソードである。「同じ量ならシミュレーションのほうが良い」という結果ではなく、「シミュレーションなら安く多く作れ、それで実機のデータに並ぶか上回る」という結果として読む。開発元による報告であり、第三者が再現した例はこの資料では確かめていない。

3.2　場面、指示、採点を LLM に作らせる

評価で手間がかかるのは、場面を数多く用意し、それぞれに正しい採点を付けることである。Genie Sim はここを LLM で自動にした。物体のアセットは 5,140 点あり、小売、工業、飲食、家庭、事務の 5 つの分野にまたがる[1]。言葉での要求から、アセットを検索して配置を決め、USD の場面を組み立てる。そのうえで指示文と採点の条件を作る。評価用の場面は 10 万を超えるとされる[4]。

2.5 節で見た scene_info.json、instructions.json、problems.json の 3 つは、この流れの生成物である。採点の条件を部品の組み合わせに限っているので、LLM が作った条件を、人が読んで確かめられる。

3.3　実際の環境を取り込む

実在の場所を撮影して 3 次元に再構成し、シミュレーションの場面として使う仕組みがある。3D Gaussian Splatting による再構成と、画像を生成するモデルを組み合わせ、見た目が写実的で、衝突の計算に使える形状も持つ環境を作る[1]。実機の評価と同じ場所をシミュレーションに持ち込めるので、3.1 節の突き合わせが成り立つ。

3.4　データを自動で作る

公開されている合成データは 1 万時間を超え、200 以上のタスクにまたがる[1]。作り方は 2 通りある。遠隔操作と、プログラムによる自動収集である。自動収集は、失敗したら戻ってやり直す仕組みを持つ。人が実機を動かして集めるデータに比べ、量と多様さを安く増やせる。

3.5　手元の評価と、公開の順位表が同じ道具

評価の仕組みは、公開の順位表 RoboColiseum の裏側でも使われている[5]。順位表は、指示理解、外乱への強さ、操作、空間理解の 4 つに分かれる。外乱への強さは、指示の言い換え、ロボットの初期姿勢、背景、画質、カメラの位置を変えて測る[1]。手元で動かした方策サーバを、同じ約束のまま順位表の評価につなげる。手元で確かめてから出せる、ということである。

3.6　道具としての作り

  • 入口が 1 つ。コンテナの起動、アセットの取得、評価の実行、状態の診断が、geniesim コマンドにまとまっている。
  • 必要な分だけ落とせる。2.7 節のとおり、タスクが参照するファイルだけを取得し、中身を確かめる。
  • 依存を固定している。コンテナに入れる Python パッケージは、ハッシュつきのロックファイルから入れる。Isaac Sim に同梱の PyTorch や CUDA を二重に入れない工夫もある。
  • AI に読ませる前提の文書がある。各部品に AGENTS.md と、作業ごとの手順書 SKILL.md が置かれ、コーディング用の AI がそのまま従えるように書かれている。人が読んでも、どこから読めばよいかがわかる。

要件のうち、世代のほかは満たせる。Isaac Sim の GitHub にある質問への回答では、以前の版について、RTX 3090 でも動くはずだが、新しい版は古い世代で個別には試していない、とされている[7]。つまり「動く見込みは高いが、保証はない」が正確な位置づけである。不具合が出たときに、対象外の世代として扱われることはありうる。Ubuntu 22.04 への対応は、今後の版で終わる予定とされている[3]。

4.2　libuipc が使えない

libuipc は、布や袋のような変形する物体の接触を解くソルバである。Genie Sim は、ビルド済みのものを GPU の世代ごとに配っていて、対応は RTX 40 系（計算能力 8.9）と RTX 50 系（12.0）だけである。RTX 3090 は 8.6 で、対象に入らない[1]。影響は 2 か所に出る。

場面起きること対処
イメージを手元でビルドするCLI が GPU を調べ、「Unsupported host GPU capability '8.6'」で止まるビルド済みイメージを使う。または --build-arg LIBUIPC_SM=89 を付ける。ビルドは GPU を使わないので通る
コンテナを起動するログに「libuipc unavailable」と出るそのままでよい。起動は続く

動かなくなるのは、runtime が libuipc の 3 タスクである。ハンガーに布をかける、巾着袋、布をたたむ、の 3 つで、どれも多指ハンドのタスクに属する。PhysX で動く 145 タスクは、libuipc を読み込まない（コードで確認した）。

4.3　VRAM の見通し

評価のときに GPU を使うのは、主に描画である。剛体の物理は、ほとんどのタスクで CPU で計算する。ロボット G2 のカメラは 3 台で、解像度は頭が 640×400、両手首が 640×528 と小さい。画面なしで動かせば、表示用の描画も減る。最小要件が 16 GB であることと合わせると、24 GB には余裕がある見込みである。

ただし、実測はしていない。このリポジトリのスクリプトは、実行のあいだ nvidia-smi の値を記録し、終わりに最大値を表示する。最初に動かしたときに、この値を確かめる。足りないときに効く手は、ほかに GPU を使っているもの（ブラウザ、別の学習）を止める、画面なしで動かす、の 2 つである。

4.4　3090 が 2 台あるときの分け方

評価プログラムと方策サーバは、ネットワークでつながる別々のプロセスである。3090 を積んだ PC が 2 台あるなら、1 台をシミュレーションに、もう 1 台を方策に使うのがよい。1 枚の GPU で描画と推論を取り合わずに済む。

PC動かすものGPU の使いみち
1 台目Genie Sim のコンテナ（評価プログラムと Isaac Sim）描画
2 台目方策サーバ。評価をしないときは学習推論、学習

方策の大きさの目安を挙げる。Genie Sim の説明では、基準として配られている π0.5 の方策は、推論のとき 1 つあたり 8 GB 未満で動く[1]。3090 で足りる。学習は別で、π0 系を LoRA で調整するのに 22.5 GB を超える VRAM が要るとされ[8]、24 GB では際どい。ACT や Diffusion Policy のような小さな方策は、学習も推論も 3090 で回せる。

4.5　画面なしで様子を確かめる

SSH 越しや、画面のない PC でも確かめられる。使えるのは次の 3 つである。評価の設定は、--benchmark.名前=値 の形でコマンドに付けて渡す。

  • カメラ画像の保存。設定 preview を真にする（--benchmark.preview=true）と、方策に渡すはずの画像 3 枚を PNG で保存して終わる。方策サーバは要らない。
  • 録画。設定 record を真にすると、頭と両手首のカメラの動画（head.webm、hand_left.webm、hand_right.webm）と、関節などの状態が残る。record_world_camera も真にすると、外から見たカメラの動画も残る。
  • 採点結果。evaluate_ret_00.json に、条件ごとの結果が残る。

画面のある PC では、--app.headless=false で Isaac Sim の画面を開ける。場面を作っている間や、不具合を調べている間は、画面があるほうが早い。

Genie Sim を動かして読むと、ロボットの方策を学習させて評価するときに要る考え方が、動く形でひととおり手に入る。ROS 2 と Gazebo の経験がある人にとっての対応づけから始める。

5.3　AgiBot の実機につながること

業務で AgiBot のロボットを使うなら、得るものがもう 1 つある。シミュレーションのロボットが、実機と同じ型だという点である。

  • 同じ機体。評価に使うロボットの中心は AgiBot の G1 と G2 で、どちらも車輪で動く双腕の機体である。観測は、頭と両手首のカメラ画像と、関節の状態という構成になっている。
  • 同じ約束で実機へ。評価プログラムには、実機向けの方策をそのままつなぐための設定（realprobe）がある。方策サーバに伝えるロボットの種類から、シミュレーションを表す接尾辞を外す。
  • データの形式。AgiBot の形式のデータを LeRobot の形式に直すコマンド（geniesim dataset convert agibot-to-lerobot）がある。LeRobot で学習する流れに乗せやすい。
  • 制御の実装が読める。全身を使うタスクでは、台車の動きを、操舵つきの各車輪の向きと速度に割り振る。この計算を二次計画法（OSQP）で解いている（pi_env.py）。MPC を学んだ人には読みやすい。

5.4　読む順路

本体は大きいが、読む順路が用意されている。一番上の AGENTS.md、source/AGENTS.md（部品の地図）、各部品の AGENTS.md、作業ごとの SKILL.md の順にたどる。評価まわりを読むなら、次の 4 つから始めるとよい。下の 3 つは、source/geniesim_benchmark/src/geniesim_benchmark/ からの位置で書いた。

6進め方

段階に分け、それぞれに「ここまでできたら次へ」の目印を置く。段階 0 から 3 は、手順書とスクリプトで進められる。

段階やること次へ進む目印
0　環境を作るPC を確かめ、本体、アセット、イメージを取得し、コンテナを起動するログに GENIESIM_READY が出る
1　描画を確かめるプレビューで、カメラ画像を 1 組保存する机、物体、ロボットの腕が写った画像が 3 枚できる。VRAM の最大値を記録する
2　一周を回す動かない方策をつなぎ、場面 1 つぶんの評価（指示 5 つ、5 エピソード）を録画する採点結果と録画ができる。点数は 0 でよい
3　2 台をつなぐ2 台目の PC で動かない方策のサーバを立て、1 台目からつなぐ段階 2 と同じ結果が、ネットワーク越しに出る
4　方策を入れ替える自分の方策サーバを書く。決まった動きを返すものから始め、学習した方策に替える録画でロボットが動く。点数が 0 より大きくなる
5　広げるタスクを増やす。データを集める。RT Engine を ROS 2 から操る業務のタスクに近い場面で、評価が回る

段階 4 の方策は、小さなものから始めるのがよい。ACT や Diffusion Policy は 3090 で学習でき、失敗の原因を切り分けやすい。大きな方策に替えるのは、データ、学習、評価の流れが一度通ってからにする。

段階 5 の RT Engine は、評価用に取得したアセットだけでは動かない。対話型の場面は別のアセットを参照するので、アセットの全体を取得し、ROS 2 のワークスペースをビルドする必要がある。
